# CODEX Review — 2026-05-24

Scope: this review treats the active Next.js / TypeScript Switchback app as the source of truth and treats the Python agent path as legacy unless the team explicitly revives it.

## Highest-priority findings

1. High — `app/page.tsx` is still the stock Next starter, so none of the built subscription, auction, card, or cancel flows are reachable from the real app entrypoint.

2. High — `lib/backboard.ts` and `.env.example` appear out of contract with Backboard's current API. The repo uses:
   - `https://api.backboard.io`
   - `Authorization: Bearer ...`
   - `POST /v1/chat/completions`

   Current docs checked on 2026-05-24 use:
   - `https://app.backboard.io/api`
   - `X-API-Key: ...`
   - `POST /threads/messages`

   Impact: `app/api/cancel/route.ts` is likely falling back most of the time instead of using Backboard successfully.

   Sources:
   - https://docs.backboard.io/authentication
   - https://docs.backboard.io/concepts/messages

3. High — `app/api/cancel-live/route.ts` still depends completely on a local Python sidecar at `http://localhost:8001`. That does not match the current non-Python direction and is not deployable as-is.

4. High — `app/api/cards/route.ts` assumes expanded PAN / CVC retrieval is a test-mode demo path. Current Stripe Issuing docs say full number / CVC retrieval for virtual cards is a live-mode capability, and Stripe recommends Issuing Elements for display.

   Impact: the current Stripe demo assumptions are likely wrong, and the comments should not be trusted as implementation guidance.

   Sources:
   - https://docs.stripe.com/issuing/cards/virtual
   - https://docs.stripe.com/issuing/elements

## Medium-priority findings

5. Medium — `components/VirtualCardReveal.tsx` never renders `card.cardNumber`; it always shows a masked `last4` value. Even if Stripe returns the full card number, the UI never actually reveals it.

6. Medium — `app/api/cancel/route.ts` with `lib/savings-state.ts` is not idempotent. Every retry or double submit increments cumulative savings again. The route also computes `const cumulative = addAnnualSavings(...)` and then ignores that variable.

7. Medium — `components/AuctionModal.tsx` uses `Math.random()` during render for the auction ID. In a Next Client Component this can create hydration mismatch warnings and changes on every re-render.

8. Medium — `components/SubscriptionCard.tsx` hardcodes `via Crave` for every replaced subscription. If the accepted bid is Tubi or Apple TV+, the UI will still claim Crave.

## Lower-priority findings

9. Low — `app/api/voice/route.ts` returns plain text `"mock-audio"` with status `200`, and `components/VirtualCardReveal.tsx` still creates an `Audio` object from that response. The fallback is brittle, and the created object URL is not revoked.

10. Low — `README.md` is stale create-next-app boilerplate and does not describe the real app, env vars, active architecture, or current run path.

11. Low — `.env.example` still encodes the older Backboard base URL assumption and does not mention `AGENT_BASE_URL`, despite `app/api/cancel-live/route.ts` depending on it.

## Legacy-path issues worth noting

12. Low, legacy — if the Python folder remains in the repo, `agent/cancel.py` imports `langchain_openai`, `langchain_anthropic`, and `langchain_google_genai`, but `agent/requirements.txt` does not install them.

13. Low, legacy — `agent/main.py` says to run on port `8000`, while the actual service and `agent/README.md` use `8001`.

## Validation notes

- Source-level review completed across the active app routes, shared libs, and major UI components.
- `pnpm install --frozen-lockfile` completed successfully enough to hydrate packages.
- Further `pnpm exec tsc --noEmit` and `pnpm exec eslint .` validation was blocked by pnpm repeatedly trying to recreate the module tree in this environment, leading to:
  - no-TTY module purge protection
  - registry access failures (`ECONNREFUSED`) on some runs
  - `EEXIST` / `EBUSY` symlink issues in `node_modules` on later runs

This means the review above is grounded in direct code inspection plus current vendor docs, but not a clean final typecheck/lint pass.

## Recommended order of work

1. Wire `app/page.tsx` so the demo has one real path through the app.
2. Decide on the cancellation architecture and remove the dead branch:
   - TypeScript-native browser automation
   - or explicit sidecar-based local demo path
3. Rewrite or remove the current Backboard client so its API contract matches the current docs.
4. Fix the Stripe virtual-card display story before relying on it for a live demo.
5. Make cancel actions idempotent and move savings state somewhere persistent or explicitly demo-scoped.
6. Sync `README.md`, `.env.example`, and `CONTEXT.md` with the actual repo state.
